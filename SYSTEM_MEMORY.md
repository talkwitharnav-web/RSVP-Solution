# SYSTEM_MEMORY.md

Current technical truth for the RSVP app. Narrative history and working-style notes live in `CLAUDE.md`.

## Stack

- Next.js 16 (App Router), React 19, TypeScript, Tailwind CSS v4 — scaffolded via `create-next-app` on 2026-07-23.
- PostgreSQL via `pg` (no ORM), connection via `DATABASE_URL` env var.
- `nanoid` for short public slugs, `qrcode` installed but **still not imported anywhere**, `lucide-react` for all icons (never emoji — see UI and Design Rules), `ws` for the WebSocket server/client, `bcryptjs` for hashing user passwords (pure-JS, chosen over native `bcrypt` to avoid Windows build friction), `heic2any` (client-only, dynamic `import()`) to transcode HEIC/HEIF photos to JPEG in-browser before upload, `recharts` for the Statistics pie chart, `fabric` (v7, added 2026-07-28) as the canvas engine behind the designed-template invitation editor — see "Designed-template invitations" below. `react-rnd` (used by the original designed-template slot editor) was removed when that editor was rebuilt on Fabric.js.
- Own modules worth knowing before writing anything new: `src/lib/validation.ts` (input bounds + `bodyTooLarge`), `src/lib/design-templates.ts` (occasion templates), `src/lib/design-palettes.ts`, `src/lib/design-fonts.ts`, `src/lib/design-icons.ts`, `src/lib/design-types.ts` (`sanitizeDesignConfig`).
- Dev server: `npm run dev` runs `node server.js`, pinned to **port 3001**, not the Next.js default 3000 — the user's other project (restaurant order tracker) already runs on 3000, and both projects may run side by side. `npm run start` also runs `server.js`. All scripts (`scripts/*.sh`, `scripts/*.ps1`) and docs reference 3001.
- **Custom `server.js`** (CJS, project root) wraps Next and hosts a raw `/ws` WebSocket endpoint — required because plain `next dev`/`next start` can't host a raw WS upgrade. Same-origin check on the WS upgrade (Origin header must match Host); no LAN/non-browser exception yet (unlike the reference project, RSVP has no non-browser client). Broadcasts a `{type: "heartbeat", status: "healthy", at: <ms>}` message every 10s to all connected clients (`globalThis.__rsvpWsClients`), plus one immediate heartbeat on connect. Also exposes its own `broadcast()` function on `globalThis.__rsvpBroadcast` (added 2026-07-24) so API route handlers — which run in the same Node process but through Next's request handler, not `server.js`'s own code — can push a live WS message without holding a WebSocket client themselves; see "Auth" and "WebSockets" sections below. `eslint.config.mjs` has a scoped override allowing `require()` in `server.js` only (it's a plain CJS entrypoint, not bundled by Next).
  - **Gotcha**: `server.js` only runs its top-level code once at process boot — it is not hot-reloaded by Next's dev-mode HMR. Editing `server.js` (e.g. adding the `__rsvpBroadcast` assignment) requires a full dev-server restart before API routes can see the new `globalThis` value; a plain file save is not enough. Confirmed via a `hasBroadcastFn: false` → restart → `hasBroadcastFn: true` check on 2026-07-24.
  - **LAN-reachable (2026-07-27)**: `server.js` binds to `0.0.0.0` (via `HOST` env var, default `"0.0.0.0"`) instead of localhost-only, so the app is reachable from other devices on the same network at `http://<this-machine-LAN-IP>:3001` — needed to test under real external-network conditions, not just from the machine running the server. `server.js` also stamps the real client socket address onto the `x-forwarded-for` header on every incoming request (always overwritten, never trusts an inbound value) before handing off to Next, since App Router route handlers have no other way to read the raw socket — this is what `src/lib/rate-limit.ts` and `src/lib/network.ts` key off. **Admin surfaces are deliberately excluded from this LAN exposure** — see "Localhost-only admin gate" below. `server.js` prints the machine's real LAN IP at boot (via `os.networkInterfaces()`, filtering out WSL/Hyper-V/link-local adapters) rather than a `<this-machine-IP>` placeholder, and caps WS clients at 200 with a ping/pong liveness sweep so half-open sockets get reaped.
  - **`allowedDevOrigins` is what actually makes LAN work (2026-07-28)**: binding to `0.0.0.0` was never the blocker. Next.js 16 blocks cross-origin requests to `/_next/*` dev assets by default, so loading the app from the LAN IP served the page HTML with a clean 200 and then refused every JS/CSS chunk — a blank page that looks exactly like "the server isn't reachable". `next.config.ts` now sets `allowedDevOrigins`, populated at startup from `os.networkInterfaces()` (so a DHCP lease change doesn't silently break it again) plus `192.168.*.*`/`10.*.*.*`/`172.16.*.*` wildcards. Dev-only; no effect on a production build and it does not weaken the localhost-only admin gate, which is a per-request IP check. The Windows Firewall rule (`scripts/allow-lan.ps1`, also `npm run allow-lan`) is separately required for **other devices** (a phone) to connect at all — it needs an elevated shell, is scoped to `LocalSubnet`, and covers both Private and Public profiles because Windows commonly classifies home Wi-Fi as Public. **Testing trap**: a request from this machine to its own LAN IP does not traverse the inbound firewall, so a "LAN works" check run locally proves app logic but not phone reachability.

## Environment

- Local Postgres runs via Docker: `docker-compose.yml` defines a single `postgres:16` service, container name `rsvp-postgres-1`, port `5432`, db `rsvp_dev`, user/pass `postgres`/`postgres`, data in the named volume `rsvp-postgres-data`. Start with `docker compose up -d`, matching the other project's Docker-based local Postgres.
- Copy `.env.local.example` to `.env.local` (`DATABASE_URL=postgres://postgres:postgres@localhost:5432/rsvp_dev` — already matches the compose defaults). `.env*` is gitignored.
- `npm run dev` needs the container up first; `initDb()` migrates on first DB access per process, same as the other project.

### One-command start/stop

- `npm run start:all` (or `startup.cmd`, or `scripts/startup.ps1`/`.sh`): checks Node/npm/Docker, auto-launches Docker Desktop if needed (up to 90s wait, also brings up WSL), creates `.env.local`/installs deps if missing, starts Postgres, waits for it to accept connections, runs `npm run dev`.
- `npm run stop:all` (or `shutdown.cmd`, or `scripts/shutdown.ps1`/`.sh`): stops port 3001, stops the Postgres container (data preserved), **then fully quits Docker Desktop and runs `wsl --shutdown`** — machine-wide, not just this project, by explicit user request. Shuts down Docker Desktop gracefully via `docker desktop stop --timeout 30` (never `--force`), not a hard process kill — a hard kill was tried first and left `vmmemWSL` running since Docker's own WSL-backend teardown never got to run; force-kill is kept only as a fallback if the `docker` CLI is unavailable.
- `npm run db:up` / `db:down` alias `docker compose up -d` / the same full shutdown as `stop:all` (`db:down` also quits Docker Desktop + WSL, not just the container).
- Shared progress-bar/output-formatting helpers live in `scripts/_common.sh`/`.ps1`, sourced by both scripts rather than duplicated. Full cold-start-to-shutdown cycle live-verified on both the bash and PowerShell paths.

### Data model

`src/lib/db.ts` owns the Postgres pool (memoized on `globalThis` in dev to survive HMR) and `initDb()`, an idempotent migration runner memoized per-process — same shape as the reference project's `initDb()`. Called at the top of every route/page that touches the DB.

**`events`**
- `id UUID PK`, `slug TEXT UNIQUE` (nanoid, 8 chars, non-ambiguous alphabet — see `src/lib/slug.ts`)
- `kind TEXT CHECK IN ('external_link', 'hosted_template', 'custom_card', 'designed_template')`
- `title TEXT NOT NULL`, `host_name`, `description`, `event_date TIMESTAMPTZ`, `location`
- `external_url` — set only when `kind = 'external_link'`
- `questions JSONB` — array of `RsvpQuestion` (`{ id, label, type: 'text'|'boolean', required }`), set only when `kind = 'hosted_template'`
- `card_image_url TEXT` — a data URL (`data:<mime>;base64,...`), set only when `kind = 'custom_card'`; see "Image uploads" below
- `created_by UUID FK -> users(id) ON DELETE SET NULL` — the sender who owns this invitation
- `guest_categories JSONB DEFAULT '["Adults", "Kids"]'` — sender-defined category labels for the "how many of each" guest-count breakdown; see "Guest categories" below
- `published BOOLEAN DEFAULT false` — gates `/receiver/[slug]` and RSVP submission; only ever flips `false → true` via `PUT /api/events/[slug]` (see Routes table)
- `created_at TIMESTAMPTZ DEFAULT now()`

**`rsvps`**
- `id UUID PK`, `event_id UUID FK -> events(id) ON DELETE CASCADE`
- `guest_name TEXT NOT NULL`, `attending BOOLEAN NOT NULL`, `guest_count INTEGER DEFAULT 1` — stored derived sum of `category_counts`, kept for backward compatibility with anything reading it
- `category_counts JSONB DEFAULT '{}'` — per-category breakdown keyed by the event's own `guest_categories` at submission time (e.g. `{"Adults": 2, "Kids": 1}`)
- `answers JSONB DEFAULT '{}'` — keyed by the event's `questions[].id`
- `created_at TIMESTAMPTZ DEFAULT now()`
- Index on `event_id`

**`users`**
- `id UUID PK`, `name TEXT NOT NULL`, `username TEXT UNIQUE NOT NULL`
- `password TEXT NOT NULL` — bcrypt-hashed
- `raw_password TEXT` — dev-only plaintext mirror, same intentional technical-debt pattern as the reference project's `restaurants` table
- `created_at TIMESTAMPTZ DEFAULT now()`
- Linked to `events` via `events.created_by` — a sender's dashboard (`GET /api/sender/events`) shows only the events they created.

Types mirrored in TypeScript at `src/lib/types.ts` (`EventRecord`, `RsvpRecord`, `EventKind`, `RsvpQuestion`, `UserRecord`).

**Migration idempotency gotcha**: `migrate()` re-runs its full body whenever `initPromise` resets (every dev-server restart, or a Turbopack Fast Refresh reload of `db.ts`). Every `ALTER`/constraint statement must tolerate re-running against a DB that already has the change applied. Concretely bit us once: a constraint drop-then-add split across two separate `pool.query()` calls left a race window where a second `migrate()` could see the constraint gone and fail re-adding it. Fix: combine drop+add into one multi-statement query so they run as a single round trip — do this for any future constraint change too.

**Image uploads** (`src/lib/image-upload.ts`): a real codec allowlist, not a loose `image/*` check — accepts PNG/JPEG/WebP/GIF/AVIF (`ACCEPTED_IMAGE_TYPES`), enforced both client-side (`isAcceptedImageType`, the upload form) and server-side (`isAcceptedImageDataUrl`, inspecting the data URL's own declared MIME prefix in `POST /api/events` and `PUT /api/events/[slug]`) since a direct API call bypasses the client picker entirely. SVG is deliberately excluded — it can embed `<script>`/event handlers and isn't sanitized before being rendered back on the public guest page, a real stored-XSS path. HEIC/HEIF (the default iPhone photo format, which no browser decodes natively) is auto-transcoded to JPEG client-side via `convertHeicToJpeg()` (dynamic `import("heic2any")`, client-only — never imported into a server route, since the library touches browser-only globals at module load).

**5MB is a compression target, not a rejection (2026-07-28)**: per explicit user instruction, an oversized image is compressed down to fit rather than refused. `prepareImageForCanvas()` (1600px longest edge, for design-canvas objects) and `prepareCardImage()` (2400px, for a bring-your-own card, which is the whole invitation) decode the file, cap the longest edge, and re-encode to WebP — falling back to JPEG where a browser refuses WebP from a canvas — stepping quality down (0.85 → 0.4) and then halving dimensions until the data URL fits `MAX_IMAGE_DATA_URL_LENGTH`. WebP is preferred because it preserves transparency at a fraction of PNG's size. `isAcceptedImageDataUrlSize()` remains the server-side backstop for a direct API call. Verified: a 5.2MB source is accepted and stored at ~1.7MB. This also protects the design as a whole — Fabric embeds image data inline in `canvasJSON`, so a raw phone photo used to push a whole card past its stored-size cap (see the data-loss note under "Designed-template invitations").

**External RSVP link scheme validation (2026-07-27)**: `POST /api/events` rejects any `external_link` event whose `externalUrl` isn't `http:`/`https:` (parsed via `new URL()`) — previously only checked for non-empty, so a sender could store a `javascript:` URL that would execute in a guest's browser on click. `GuestEventView`'s `isSafeExternalUrl()` re-checks the same condition before rendering the "RSVP now" `<a href>`, as defense in depth against any pre-existing bad data. **`PUT /api/events/[slug]` now accepts `externalUrl` too (2026-07-28)** with the same validation — the URL was previously frozen at creation with no edit path at all; `EventEditor` shows an "RSVP link" field for `external_link` events.

**Input bounds** (`src/lib/validation.ts`, added 2026-07-28): every text field that reaches the database is length-bounded, truncating rather than rejecting (same clamp-don't-reject posture as `sanitizeDesignConfig`). Username 64, person name 120, title 200, short text (host/location) 300, long text (description) 5000, URL 2048, RSVP answer 2000, guest categories 12 × 40, questions 20 × 200-char labels. Matching `maxLength` attributes on the inputs so a sender sees the limit rather than silent truncation. Also exports `bodyTooLarge(req, max)` — route handlers previously buffered request bodies with no upper bound at all; 64KB on credential/simple routes, 16MB on the two that legitimately carry an image or a serialized canvas, returning 413.

**Guest categories** (`src/lib/guest-categories.ts`): `parseGuestCategories(raw)` turns a sender's free-typed "Adults, Kids, Moms, Dads, Pregnant Penguins" into a trimmed, empty-token-filtered array, falling back to `DEFAULT_GUEST_CATEGORIES` (`["Adults", "Kids"]`) if nothing usable was typed. Applies to any RSVP-taking event kind (`hosted_template`/`custom_card`); the editor skips the field entirely for `external_link` events, which never show the hosted RSVP form. The guest-facing `RsvpForm` renders one number input per category plus a live-computed, non-editable total ("Adults + Kids = N"), generalized to however many categories the event defines.
- **Singular labels for a count of one (2026-07-28)**: `categoryLabelForCount(category, count)` returns the singular form when `count === 1`, so the statistics view reads "1 Kid", not "1 Kids". Categories are free-typed, so this can't be a lookup table — it's a deliberately conservative reverse-pluraliser that only touches the **last word** ("Pregnant Penguins" → "Pregnant Penguin"), knows four irregulars (children/people/men/women), handles `-sses/-xes/-zes/-ches/-shes` and `-ies`, and **leaves anything it isn't confident about unchanged** — an untouched label is a far smaller blemish than one mangled into a non-word. Deliberately not applied to the RSVP form's own field labels, which name a category rather than count one.

**Statistics view** (`src/app/sender/StatsModal.tsx`): a donut of per-category guest counts plus a per-guest breakdown list, live-refreshed off `db-changed`. Three changes 2026-07-28: (1) **declines are represented**, both as their own "Can't come" slice (counted one person per declining response, since a decline carries no category counts) and as a row in the breakdown — previously a guest who answered "no" vanished from the sender's view entirely, leaving no evidence they'd replied at all; the decline slice is a desaturated neutral rather than a fourth hue, because the validated palette only has three slots that survive the all-pairs CVD/contrast gates and "not attending" isn't a guest category anyway. (2) Counts of exactly one use the singular label (above). (3) **Each row can be deleted** — a guest can only submit, never edit, so fixing a wrong answer is the sender's job. The delete is optimistic, and uses an **inline** two-step confirm ("Remove? Yes / Cancel") rather than a nested `Modal`, since this view is itself a modal and stacking two backdrops means one stray click can close both; shift-click skips the confirm, matching the admin tables.
- **Per-category count cap + input fixes (2026-07-27)**: each category's count is capped at `MAX_CATEGORY_COUNT = 999`, enforced both client-side (`RsvpForm.tsx`'s `CategoryCounts`, via `Math.min` in its `onChange`) and server-side (`POST /api/events/[slug]/rsvps`, same constant) — previously uncapped, so a client could type or a direct API call could send an arbitrary value like `999999999` and it would be stored as-is (aside from being floored to a non-negative integer). Also fixed two input UX bugs in the same component: the field previously always rendered `value={counts[category] ?? 0}`, a plain number, which caused a visible "01" while typing a fresh digit into a zeroed field (typing "1" briefly showed "01" as React reflowed the controlled value) — fixed by rendering the raw typed digit string directly (empty string shown as a `0` placeholder, not a real `0` value) instead of round-tripping through `Number()` on every keystroke. The Total display box was also a fixed `w-20`, which visibly overflowed for large totals — changed to `min-w-20 w-fit` so it grows with its content instead of clipping.

**Designed-template invitations**: a fourth `EventKind`, `designed_template` — the "Design in our editor" flow. Originally built 2026-07-27 as a template-constrained `react-rnd` slot system (3 fixed layouts, drag/resize named slots within guardrails); **rebuilt 2026-07-28 on a real Fabric.js canvas** after user feedback that the slot system couldn't add new text boxes, duplicate icons, or drop in arbitrary images — see `custom rsvp card designer.md` for the fuller history of both versions. Current mechanism:
- `events.design_config JSONB` (nullable, only set for this kind) stores `{paletteId?, fontPairId, colors, canvasJSON, canvasWidth, canvasHeight}` — `src/lib/design-types.ts`'s `DesignConfig` type. `canvasJSON` is Fabric's own `canvas.toObject(propertiesToInclude)` scene graph (objects, positions, colors, text content, embedded images as data URLs) — no custom scene-graph parsing is written or maintained; `canvasWidth`/`canvasHeight` fix the logical coordinate space so the same JSON renders identically at any container size. The old `templateId`/`slots`/`iconId` shape and `src/lib/design-templates.ts` were deleted outright (fresh start, no migration path for pre-rebuild designed_template events — confirmed acceptable with the user since the feature was still brand new).

- **Fonts reaching the canvas — two separate bugs, both fixed 2026-07-28.** (1) `FabricCanvas` originally created text with no `fontFamily` at all, so all 30 pairs and ~50 loaded families were decorative and every card drew in Fabric's default. Canvas 2D's `ctx.font` also cannot resolve a CSS custom property, so passing `var(--font-design-x)` fails silently — `resolveFontFamily()` (`design-fonts.ts`) reads the variable's real value off `document.documentElement` via `getComputedStyle`, and `ensureFontsLoaded()` awaits `document.fonts.load()` because a canvas draw does not itself trigger a `next/font` file fetch. (2) Even with the family correct, the card still didn't change: `obj.set({fontFamily})` updates the property and Fabric's *measuring* context but leaves the object painting from its cached bitmap, and `canvas.requestRenderAll()` defers to `requestAnimationFrame`, **which browsers throttle to a standstill whenever the tab isn't foregrounded**. `applyFontPair()` therefore does `set()` → `initDimensions()` → `setCoords()` → `dirty = true` and then calls **synchronous `canvas.renderAll()`**, not `requestRenderAll()`. Same treatment in `setSelectedTextProps`. Any future discrete, user-triggered canvas mutation should render synchronously for the same reason. The resolved family name is deliberately **never** stored in `canvasJSON` — the stable `fontPairId` is stored and re-resolved after every `loadFromJSON`, which also fixes the guest page where nothing else would trigger a corrective re-render.
- **`Textbox`, not `IText` (2026-07-28)**: all text (new and template-created) is `fabric.Textbox` with a bounded width (80% of the canvas for new text, 84% for template elements) so a long headline wraps inside the card instead of running off both edges, which is exactly what happened with unwrapped `IText`. `Textbox` extends `IText`, so every existing `instanceof fabric.IText` check (font application, text-property panel) still matches.
- **Occasion templates** (`src/lib/design-templates.ts`, 2026-07-28) — the "pick an occasion, then nudge it" first step every researched competitor has. Five: Birthday, Wedding, Formal Event, Party, Informal Get-together. Each declares `colors`, a `fontPairId`, and a list of positioned **elements** (percent coordinates, `fontSizePct`, and a colour *role* name rather than hex) — deliberately **not** raw serialized Fabric JSON, which is brittle across library versions; `FabricCanvas.applyTemplate()` builds them through the same add-paths a manually-created element uses, so nothing a template produces is special, locked, or able to drift from hand-built behaviour. Applying replaces the canvas contents and sets colours + font pair together. Verified: all five produce distinct cards, nothing exceeds the card bounds (max 841px in a 1000px canvas), and a template round-trips through save → publish → guest page. `public/design-assets/` is still empty — templates reuse the existing icon/decoration registries rather than shipping new artwork.
- **Theme-change prompt + suggested fonts (2026-07-28)**: clicking a colour preset only changes the card's colour *settings*; objects already on the canvas keep their own colours, which isn't what a sender expects. An `isDirty` flag drives a `beforeunload` warning, since nothing autosaves.
- **Text styling panel**: `getSelectedTextProps()`/`setSelectedTextProps()` expose font size, bold, italic, underline and alignment, shown in the Elements tab only when the selection is a text object so the controls can't appear to do nothing on an image. Line height and letter spacing are still not exposed.
- **Per-character text styling (2026-07-28)**: bold/italic/underline, colour and font can be applied to *part* of a text object, not just the whole box. Backed by Fabric's own `setSelectionStyles`/`getSelectionStyles` keyed off `selectionStart`/`selectionEnd` while the object is in edit mode; with no range selected the change falls back to the whole object. `Ctrl+B` / `Ctrl+I` / `Ctrl+U` are wired for both cases. **Fabric drives text editing through its own hidden `<textarea>` (tagged `data-fabric="textarea"`), so the "is the user typing in a form field" guard in `handleKeyDown` must exclude that one element** or every shortcut is dead exactly when text is being edited. `src/components/design/SelectionFontPicker.tsx` is the searchable per-selection font list; the panel label switches between "Whole text box" and the selected range.
  - **Serialization landmine**: Fabric groups adjacent characters into ranges for storage using a **fixed whitelist** of style properties (`fill`, `stroke`, `strokeWidth`, `fontSize`, `fontFamily`, `fontWeight`, `fontStyle`, `underline`, `overline`, `linethrough`, `deltaY`, `textBackgroundColor`, `textDecoration*`). A custom key is *kept* inside a style entry but is **not** consulted when deciding where one range ends and the next begins — so two neighbouring runs differing only by a custom marker get merged and one is silently lost. `CHAR_FONT_KEY` (`"fontKey"`) therefore always rides alongside a real `fontFamily`: the family makes the run boundary detectable, the marker is the source of truth, and `reresolveCharacterFonts()` re-derives the family from the marker after every load (same "never trust a stored font family" rule the object level follows).
- **Auto-width text boxes (2026-07-28)**: text boxes size themselves to the text actually in them (`fitTextboxToContent()`, capped at `TEXT_MAX_WIDTH_FRACTION` = 84% of the card). Previously every box was created at a flat 80% of the card width regardless of content, so a short heading sat in an 800px box with ~180px of dead space each side. That also made resizing *look* broken: text is centred inside its box, so dragging the right handle inwards re-centres the visible text leftward even though the left edge never moves — measured and confirmed, the left edge held at 99.99995 of 100. Hugging the content removes the dead space the text was re-centring within. Measuring happens at the **maximum** width first, because `calcTextWidth()` reports the widest *wrapped* line — measuring at the current (already narrow) width would just report that width and the box could never grow back. State lives in a custom `autoWidth` flag (in `CUSTOM_OBJECT_PROPS`, so it round-trips); it is switched **off** when `object:modified` reports `action === "resizing"`, since dragging a side handle is the sender explicitly choosing a wrap width. Corner handles scale the whole object rather than changing `width`, so they deliberately leave it alone. Re-fits on typing (`text:changed`), on font-pair change, and after a font finishes loading.
- **Snapping and alignment guides (`src/components/design/canvas-snapping.ts`, 2026-07-28)**: built on Fabric v7's official `AligningGuidelines` extension (`import { AligningGuidelines } from "fabric/extensions"` — really present in 7.4.0, no new dependency). The extension only ever aligns to *other objects*; snapping to the card itself comes from feeding it two **phantom rectangles** through its documented `getObjectsByTarget` override — one covering the whole card, one inset to a safe-area margin. Its point collector only reads `getCoords()` + `getCenterPoint()`, so a full-card rect contributes exactly x = {0, W/2, W} and y = {0, H/2, H}. The phantoms are never added to the canvas, so they can't render, be selected, or reach `canvasJSON`. Both axes snap in the same drag (verified: released 7 card-px off centre on x *and* y, landed at exactly 500/625). `margin` is in **screen** pixels — the extension divides by zoom internally, which is what keeps the snap feel constant at any zoom.
  - **Equal-spacing (distribution) guides**: `findEqualSpacing()` runs as a second pass on both axes, only considering peers that actually overlap on the *other* axis, and only adjusting an axis the guidelines left alone (edge/centre alignment is the stronger signal). Card/safe-area phantoms are excluded here — spacing is about rhythm between real elements.
  - Guide colour is picked per card by WCAG contrast between two vivid hues (magenta / cyan) against the sender's chosen background, because a fixed colour or a theme token disappears on some cards. Holding **Ctrl** suppresses snapping (Alt and Shift are already Fabric's centred- and uniform-scaling modifiers). Rotation snaps to 15° via Fabric's native per-object `snapAngle`/`snapThreshold`, stamped in the single `object:added` handler.
- **Zoom and pan (2026-07-28)**: modelled as a **multiplier on top of** the fit-to-container zoom, never a replacement. `fitZoomRef` is the fit scale, `userZoomRef` the sender's zoom (1–5, floor of 1 = "fits the panel"), and only the viewport transform moves — object coordinates are never touched. The `<canvas>` element stays the size of the fitted card and acts as a window onto the design. Verified safe: 100% → 156% left the canvas element at exactly 576×720. `viewportTransform` is not part of `canvas.toObject()`, so editor zoom/pan cannot leak into the saved design or the guest page. Ctrl/⌘+wheel zooms at the cursor; the toolbar buttons zoom about the view centre.

Added 2026-07-28 after the user reported "layers, right now it's a mess" — confirmed working end-to-end (reordering visually changes which object draws on top, e.g. two overlapping icons swapping front/back).

## Auth

Added 2026-07-24. Two independent, unrelated auth systems — ported from the reference project's own admin/kitchen split (admin credentials are recorded in `CLAUDE.md`'s "Critical — Read First" section):

- **Admin** — a single username/password pair checked in `POST /api/admin/login`, no DB row, no bcrypt. **Hardened 2026-07-28**: the comparison is now length-padded `timingSafeEqual` with both halves always evaluated (no `&&` short-circuit), since a plain `!==` leaked how much of the credential matched via response timing — the sender login already guarded against this with its dummy-hash bcrypt compare. Credentials read from `ADMIN_USERNAME`/`ADMIN_PASSWORD` env vars, falling back to the committed pair. The login form itself is inline on `/` (`AuthCard` in the gateway page's main content area when no admin session exists), not a separate `/admin/login` route — matches the reference project's own layout exactly, per explicit user instruction ("in the empty space on the right of the sidebar, it will have a login window like how restaurant has it").
- **Sender** — real, DB-backed, self-serve. `/sender/login` checks `GET /api/sender/has-account` first; if the `users` table is empty, it redirects straight to `/sender/signup` before ever rendering a login card (so a fresh install can't dead-end at a login form with nothing to log into). `/sender/signup` is a real self-serve registration form (bcrypt-hashed password, `raw_password` dev mirror, live `StrengthMeter`), auto-logs-in on success.

**SQL LIKE-wildcard auth weakness, fixed 2026-07-28** — the most serious thing found in the security sweep. Both login and register looked users up with `WHERE username ILIKE $1` using the raw user-supplied value. `%` and `_` are ILIKE wildcards, so submitting `%` as a username matched *every* row and handed back an arbitrary account for the password check, turning "guess a username **and** its password" into "guess **any one** account's password"; `_` let an attacker steer which account matched. Both now use `WHERE lower(username) = lower($1)`, which keeps the intended case-insensitive login without wildcard semantics. A `users_username_lower_idx` unique index was added in `migrate()` so the database enforces the same uniqueness the auth code assumes (the column's own UNIQUE is case-sensitive, so `Bob` and `bob` could otherwise coexist and make the lookup ambiguous); index creation is wrapped in try/catch so a dev DB with pre-existing case-duplicates warns instead of failing startup.

**Session mechanism** (`src/lib/session.ts`, ported from the reference project's own `lib/session.ts`): a stateless, signed HMAC token — `base64url(JSON payload) + "." + HMAC-SHA256(payload)` — not a JWT, not a DB `sessions` table. `verifySessionToken` uses `timingSafeEqual` on the signature and checks the payload's own `exp` claim; since 2026-07-28 it also shape-validates the parsed payload, because a token missing `exp` entirely read as "not expired" (`undefined < Date.now()` is false). `SESSION_SECRET` has a dev-only hardcoded fallback that **throws on a production build** if unset — the fallback is committed to this repo, so anyone who has seen the source could otherwise forge admin/sender cookies. Two separate cookies (`admin_session`, `sender_session`) so both roles can be logged in independently in the same browser without one login clobbering the other's cookie/remember-me duration — same rationale as the reference project's `admin_session`/`restaurant_session` split.

**Cookie options**: `httpOnly`, `sameSite: "lax"`, `secure` gated on `FORCE_SECURE_COOKIES === "true"` (explicit opt-in, not tied to `NODE_ENV`, since `NODE_ENV` reflects build mode not actual transport). **Remember Me** controls only the cookie's `maxAge` at set-time — 30 days if checked, 1 day if not (a real explicit value, not an omitted-`maxAge` session-only cookie, which the reference project found unreliable across ordinary browser navigation). The signed token's own internal `exp` is always 30 days regardless, an outer safety bound independent of cookie persistence.

**Enforcement layers** (`src/lib/auth.ts`): `requireAdmin()` / `requireSender()` are the real security boundary — every admin-gated API route calls one as its first line and returns its 401 response early if unauthorized. Pages additionally do a client-side `GET /api/session` check + redirect for UX (no flash of protected content), but that's not the actual gate — confirmed via a direct unauthenticated `curl` to `GET /api/dev/db` returning a real 401, not just a client-side bounce.

**Gated behind `requireAdmin()`**: the `/admin/db` page itself (client-side redirect to `/` if no admin session) plus its backing routes — `/api/dev/db` (GET/POST/DELETE), `/api/users/[id]` (PUT/DELETE), `/api/users/[id]/password` (PUT), `/api/events/[slug]` DELETE only.

**`GET /api/events/[slug]` is public but publish-gated (fixed 2026-07-28)**: it previously had no auth *and* no `published` check, so the entire publish mechanism was page-level only — anyone holding a slug could read a full draft straight from the API, which is exactly what publishing is meant to prevent. It now mirrors the `/receiver/[slug]` gate: an unpublished event 404s (the same 404 an unknown slug gets, so it can't be used to confirm a slug exists) for everyone except the owning sender, and `created_by` is stripped from the response.

**Gated behind `requireSender()` + ownership check** (event's `created_by` must equal the caller's `userId`, not just a valid sender session): `PUT /api/events/[slug]`, `GET /api/events/[slug]/rsvps/stats`, `DELETE /api/events/[slug]/rsvps/[id]`, `DELETE /api/events/[slug]` (2026-07-29, when the caller isn't an admin — see the routes table). **Gated behind `requireSender()` alone** (no ownership check needed — creates a new row / lists the caller's own): `POST /api/events`, `GET /api/sender/events`.

**Ghost sessions, closed 2026-07-29**: `requireSender()` used to only verify the session cookie's *signature* — that it was validly signed and correctly shaped — never that the `users` row it names still actually exists. If that account was deleted (via Access DB) while its browser still held the cookie, every route guarded by `requireSender()` kept accepting it indefinitely; the signed token itself has no idea its subject is gone, and doesn't expire early just because of that. Closed in two independent layers, since either alone leaves a real gap:
- **Live layer** (client-side, needs the tab's WebSocket to be connected): `broadcastUserDeleted`/`SessionWatcher` — see "WebSockets" above. Force-logs-out an already-open tab within about a second of the delete, with a real toast explaining why.
- **Backstop layer** (server-side, unconditional): `requireSender()` itself (`src/lib/auth.ts`) now runs one indexed `SELECT 1 FROM users WHERE id = $1` before granting access. If the row is gone, it returns `401 {"error": "This account no longer exists"}` **and** clears the stale cookie in the same response (`Set-Cookie: sender_session=; Max-Age=0`) — so a backgrounded tab whose socket dropped, a missed broadcast, or a request fired with no page/JS open at all (a bookmarked API call) all still self-correct on the very next request, not just tabs that happened to have a live connection at the right moment. `initDb()` is called inside `requireSender()` itself (not assumed already-run) since some call sites invoke it before their own `initDb()` call.

One extra indexed lookup per request against a handful of mutation/data routes (never a hot rendering path) is the cost of this guarantee holding unconditionally rather than "usually, if the tab's socket happened to be up." Verified independently of the WebSocket path entirely: deleted a user directly at the DB layer (bypassing the app's own delete route and broadcast), then confirmed a stale cookie against two different `requireSender()`-guarded routes both returned the 401 with the cookie cleared.

**Localhost-only admin gate (2026-07-27)**: now that `server.js` binds to `0.0.0.0` for LAN testing, admin-only surfaces are additionally restricted to requests originating from the machine running the server — LAN reachability was meant for the sender/receiver-facing app, not the admin console (one hardcoded credential pair, full DB read/write/purge). Two layers, both keyed off `src/lib/network.ts`'s `isLocalhostIp()`/`clientIpFromHeaders()` (reading the same `x-forwarded-for` header `server.js` stamps with the real socket address — see the LAN section above):
- **`src/proxy.ts`** (renamed from `src/middleware.ts` same day — Next.js 16 deprecated the `middleware.ts` convention in favor of `proxy.ts` for the same request-interception mechanism; the rename is a straight file/export-name swap, no behavior change, re-verified after) — matches `/`, `/admin/*`, `/api/admin/*`, `/api/dev/*`, `/api/users/*` and returns a 404 (page routes) or `{error: "Not found"}` (API routes) for any non-localhost IP, before the request reaches a page or route handler at all.
- **`requireAdmin()` (`src/lib/auth.ts`)** — independently re-checks the same localhost condition (404 if not local) before checking the session cookie. This exists because `DELETE /api/events/[slug]` shares a path with the public `GET`/`PUT` handlers on that same route, so the proxy's path-prefix matching can't gate it — `requireAdmin()` is the only enforcement point for that one route, and every other admin route gets the check twice (redundant, not a gap). This split also matches Next's own stated reasoning for deprecating `middleware.ts` (a real CVE where auth logic living only in the edge-runtime proxy layer could be bypassed under load) — this app's proxy only ever does an IP check, never session/auth verification, which has always lived in route handlers/pages instead.

Live-verified from both localhost (admin routes reachable, correct 401 when unauthenticated) and the real LAN IP (admin routes 404, sender/receiver routes still 200); a spoofed `X-Forwarded-For` has no effect since `server.js` always overwrites it with the real socket address.

**Rate limiting (2026-07-27)**: `src/lib/rate-limit.ts` — in-memory, fixed-window, keyed by client IP (via the same `x-forwarded-for` mechanism) + a bucket name, stored on `globalThis` to survive HMR like the app's other module-level state. Applied only to the routes an unauthenticated outsider can actually hit (authenticated sender/admin routes are already gated by session, so weren't given IP limits — avoids throttling the sender/testers when they share one router's IP): `POST /api/admin/login` (10/5min), `POST /api/sender/login` (10/5min), `POST /api/sender/register` (5/hour), `POST /api/events/[slug]/rsvps` (20/10min). Returns 429 with a `Retry-After` header when exceeded. In-memory (not Redis-backed) is an intentional scope decision, not an oversight — this is a single-process app, and the goal is blunting naive scripted abuse, not surviving a multi-instance deployment. A throttled sweep (2026-07-28) now deletes expired windows; they were previously reset in place but never removed, so the map grew by one permanent entry per (bucket, IP) pair forever.

**Note for testing**: the 5-signups-per-hour limit is in-memory, so restarting the dev server resets it — useful when an automated run burns through it.

## WebSockets

- `src/lib/useWebSocket.ts` — reusable client hook (connect to `/ws`, JSON parsing, reconnect with exponential backoff capped at 15s, returns `{status, messagesByType}` keyed by message `type`). Any live feature subscribes to its own `type` over this one connection rather than opening a second socket.
- `HealthPin` polls `GET /api/health` (not WS-driven) for DB round-trip latency/size/pool stats, live WS listener count (still sourced from `globalThis.__rsvpWsClients`, via HTTP now), and the client's own round-trip time. Tiered `healthy`/`ok`/`bad`/`terrible`, 10s idle / 1.5s active-popover poll cadence, debounced-250ms fetch-on-open, pauses when the tab is backgrounded. `/api/health` itself has no auth gate (matches the reference project's own kitchen-facing exposure pattern).
- **`db-changed` broadcast**: `server.js` exposes `broadcast()` on `globalThis.__rsvpBroadcast` (see Stack section). `src/lib/ws-broadcast.ts` wraps it as `broadcastDbChanged(kind: "users" | "events")`, called from every route that writes a `users`/`events` row, immediately after the write succeeds.
- **Subscribers, current as of 2026-07-29**: `/admin/db` (refetches `GET /api/dev/db`); `GuestEventView` (refetches `GET /api/events/[slug]` — a guest with the page open sees a host's live edit); `StatsModal` (refetches stats while open, so a new RSVP updates the pie chart without a manual reopen); `InvitationGallery` (refetches `GET /api/sender/events` — the whole card grid, including a brand-new invitation appearing with no manual reload); `EventEditor` and `DesignEditor` (deliberately **partial** — see below).
- **`EventEditor`/`DesignEditor` sync only the `published` flag, not the whole record (2026-07-29)**: both have real text fields (and `DesignEditor` additionally a live Fabric canvas + undo/redo stack + `isDirty`/`beforeunload` guard) a sender could be actively editing, so blindly overwriting `event`/`colors`/`canvasJSON` on every live `db-changed` would silently discard in-progress keystrokes or design work the instant a guest RSVPs or another tab edits something unrelated. Each does its own tiny `GET /api/events/[slug]` on a `db-changed` and only calls `setEvent` if `published` actually changed — verified with real CDP-simulated typing (not a raw `dispatchEvent`, which bypasses React's controlled-input path and gives a false pass/fail) that an unsaved edit survives a concurrent publish from another tab while the Published badge still updates live.
- **`user-deleted` broadcast (2026-07-29)**: a targeted companion to `db-changed`/`kind: "users"` — that one gives every connected client no reason to react to someone *else's* account being touched, but a deleted user's own already-open tab(s) need to actually know. `broadcastUserDeleted(userId)` carries the specific deleted id; `SessionWatcher.tsx` (mounted once in the root layout, so it catches this from any page) compares it against its own session's `userId` (now exposed by `GET /api/session`) and, on a match, clears the sender cookie via `POST /api/logout`, shows a toast, and redirects to `/sender/landing`. See "Ghost sessions" under Auth for the full picture, including the server-side backstop for when this live push doesn't land in time.

## Optimistic UI (client-side prediction)

`src/lib/optimistic.ts`, added 2026-07-28. The same trick multiplayer games use: the UI assumes the server will accept an action and updates immediately, the request goes out in the background, and if the server disagrees the local change is rolled back and the user is told.

- **`useOptimisticActions()`** returns `{ run, pendingCount, hasPending, pendingRef }`. `run({ apply, commit, errorLabel?, notifyOnError?, onConfirmed?, onRejected? })` — `apply()` mutates local state now and **must return its own rollback function**, which is the part that's easy to forget and the reason this is a shared helper rather than ad hoc `setX()` before each `fetch`. A rejection runs the rollback and raises an error notification (`errorLabel` is prefixed to the server's own message); `notifyOnError: false` opts out. `onConfirmed` is where the authoritative row is reconciled back in.
- **`reinsertAt(list, item, index)`** is the standard rollback for a removed list item — puts it back where it was rather than restoring a whole snapshot, so an unrelated optimistic change made in the meantime isn't resurrected with it.
- **`pendingRef` exists because of the `db-changed` refetch.** A WS-triggered reload while one of our own mutations is unconfirmed would overwrite the predicted state with server data that predates it — a deleted row flashing back into the table and then vanishing again. `/admin/db` reads `pendingRef.current` synchronously in the WS effect, defers the refetch (`missedRefreshRef`), and runs it once `pendingCount` returns to 0.
- **Where it's used**: `/admin/db` (user + RSVP-link delete, rename, password reset), `EventEditor` (save, publish), `DesignEditor` (save + publish in edit mode), `RsvpForm` (the guest's own submission), `StatsModal` (per-RSVP delete).
- **Where it deliberately isn't**: Seed/Purge on `/admin/db` (typed-confirmation destructive operations — correctness beats latency, and pretending the database is already wiped is the wrong lie to tell), and **creating** anything that ends in a redirect to a server-minted slug (`/create/design`'s create mode, `BringYourOwnCardForm`) — there's nothing truthful to show early.
- The hook calls `useToast()`, so it can only be used under the root layout's `ToastProvider` — which is everything.

- Theme is implemented per `theme.md` (full research/rationale/token table lives there). Fonts: Bricolage Grotesque (`--font-display`, headings only) + Plus Jakarta Sans (`--font-body`, everything else), loaded via `next/font/google` in `layout.tsx`. Corrected to a genuine pink-red coral and real saturated hue backgrounds (bright pink-blush light `#FDF2F5`, deep plum/wine dark `#241827`). Sage and lavender were also defined as tokens from day one but never actually referenced by any component — every accent defaulted to coral, which was the real mechanism behind the "everything looks orange" complaint. - **High contrast / CVD palette specificity bug fixed 2026-07-24**: `[data-contrast="high"]` and `[data-cvd="..."]` (specificity 0,1,0) were silently losing the CSS cascade to `:root[data-theme="dark"]` (specificity 0,1,1) whenever dark mode was active — which it is by default (`prefers-color-scheme` fallback). Found via headless-Chrome computed-style inspection (`getComputedStyle(...).getPropertyValue('--color-...')` before/after toggling the attribute), not just visual screenshot comparison, since the visual delta was subtle enough to miss by eye. Fixed by anchoring both selectors to `:root` (`:root[data-contrast="high"]`, `:root[data-cvd="..."]`) to match the theme rule's specificity.

- **Notifications (`Toast.tsx`, rebuilt 2026-07-28)**: a macOS-style notification group, **mounted once in the root layout** so any screen can raise one (it was previously a per-page provider on `/admin/db` only, so nothing else in the app could report a failure at all). Newest on top; more than one collapses into a pile of up to 3 cards with a count badge; click/Enter/Space expands; auto-dismiss is **paused while expanded** (the user is reading); the collapsed pile's “x” clears the whole group. Auto-dismiss is 4s success / 6s warning / 8s error — a failure needs longer than a confirmation. The *behaviour* is a port of the reference project's group; the *look* is not — per explicit instruction ("no bistro glaze... keep texture and everything flat like our buttons") the cards are flat solid fills on the same tokens `Button.tsx` uses, with no gradient, blur or translucency. Error-code chips and the action-button variant were left out as reference-specific. **Gotcha**: the stack's position/scale lives on a wrapper element, not on the animated card — `animation-fill-mode: both` on `notification-pop-in` keeps overriding an inline `transform` even after the animation ends, which silently flattens the pile (the same trap `ThemedTooltip` hit). `.toast-stack` is pinned to the true top-right corner and deliberately overlays the Settings pill while visible — confirmed acceptable, it's a temporary overlay.
- **`PageHeader` gained a `noClearTopRight` opt-out prop 2026-07-24**, used by `/admin/db` only. The pill is a `fixed` overlay — it should draw on top of other UI when it expands, not have other UI live-shift to avoid it. `clear-top-right`'s reserved-space padding is driven by a CSS var that updates as the pill expands/collapses, which on `/admin/db` (a header with a busy action row: Seed/Purge/Back) was visibly shoving the action buttons left in real time. Fixed by having that page opt out of `clear-top-right` entirely and instead give its one genuinely crowded button (Purge Database) a small **static** `mr-14` margin — just enough clearance from the pill's *collapsed* resting position, that doesn't grow/shrink as the pill opens. The transient hover/tap health-detail popover still briefly overlaps the header when open — treated as acceptable, same category as any tooltip/dropdown overlapping content while open, not a persistent layout issue.
- Small reusable primitives ported/reskinned from the reference project: `Button`, `Card`, `PageHeader`, `ThemedTooltip` (hover tooltip driven by React state, not the native `title` attribute).
- **`ThemedTooltip` positioning rewritten 2026-07-28** after tooltips appeared far to the left of their trigger. It renders as **two nested elements on purpose**: the outer owns `position: fixed` (so a trigger inside a scrolling panel can't be clipped by that panel's overflow) plus the centring `translateX(-50%)`; the inner owns the `dropdown-reveal` animation. They cannot be the same element — `dropdown-reveal-in` animates `transform`, and **a CSS animation overrides an inline `transform`**, which silently discarded the centring and left every tooltip offset by half its own width. An earlier attempt to centre by subtracting half of `max-width` was also wrong, since the box is `w-max` and its real width isn't known until it renders. Viewport clamping happens in a `useLayoutEffect` once the real width is measurable, and only when the box would actually overflow. Labels wrap (`break-words`) because tooltips also surface full values truncated elsewhere in the UI.
- Several `react-hooks/set-state-in-effect` ESLint findings are intentionally suppressed (with inline comments explaining why) in `ThemeToggle`, `UiSizeToggle`, `AccessibilityMenu`, `useDropdownReveal`, `HealthPin` — each is syncing to real DOM/localStorage state on mount (unavoidable without diverging from SSR) or an external system tick, matching the reference project's own documented precedent for the identical pattern. Not blanket-disabled — each site has its own comment.
- **Custom 404 page (2026-07-27)**: `src/app/not-found.tsx`, themed to match the rest of the app (wordmark, coral "404", the settings pill still renders on top of it since it's globally mounted) instead of the default Next.js error page. As a single global file (App Router convention), it catches both unmatched routes and every existing `notFound()` call in the app (an unknown `/e/[slug]`, an unpublished `/receiver/[slug]` viewed by a non-owner) — no per-route 404 files were needed given the app's small route surface.
- **Tailwind v4's Preflight resets `button { cursor: default }`** (an intentional upstream accessibility-motivated change from earlier Tailwind versions) — every native `<button>` in this app was showing the plain arrow cursor instead of the pointer/"clicky" cursor on hover until this was caught and fixed 2026-07-24. Fixed globally in `globals.css` with `button:not(:disabled), [role="button"] { cursor: pointer; }` rather than patching each component's className individually. If a future button still shows the wrong cursor, check whether it's disabled (correctly gets `cursor-not-allowed` instead, see `Button.tsx`) before assuming the global rule broke.
- **`ThemedTooltip` avoids all four viewport edges (bottom flip added 2026-07-28)**: it already clamped horizontally, but always rendered *below* its trigger, so the editor's zoom controls — which sit a few pixels off the bottom of the window — had their tooltips sliced off (measured at bottom 911 in a 900px viewport). It now flips above the trigger when there isn't room below, and only when there's genuinely room above. Placement is measured once per hover in a `useLayoutEffect` and left at the default when nothing overflows, so the common case stays a single render.
- **`devIndicators: false` in `next.config.ts` (2026-07-28)**: hides Next's floating dev-tools badge, which lives in the bottom-left — exactly where `/create/design` puts "Create Invitation" and `/sender` puts "Log Out", so it covered a primary button on two screens. Dev-only UI; it never rendered in a production build. **Changing `next.config.ts` needs a full dev-server restart**, not just a page reload.
- **Filter rows on `/admin/db` are single-row**: the search box used to be `w-full max-w-xs` inside a `flex-wrap` row, so it claimed the whole row and pushed "Clear filters" onto a second line where it floated orphaned between the search box and the table (row height 94px vs 50px now). Search boxes are a definite `w-72` and the controls row no longer wraps.

## Explicitly NOT built yet

- No un-publish / take-down control — publishing is one-directional by design (see Routes table's `PUT /api/events/[slug]` note); there's no way for a sender to pull a link back to draft once it's live.
- No host-facing guest list view beyond the Statistics pie chart + per-guest breakdown card — no CSV export, and no search/filter within a single event's RSVPs. Individual RSVPs **can** now be deleted from that card (2026-07-28), but not edited. A whole invitation (not just one RSVP row) can also now be deleted by its owning sender directly from the gallery card (2026-07-29, confirm modal + shift-click to skip), not just by an admin from Access DB.
- No visual template customization beyond the custom-card image + guest-categories text field for `custom_card`/`hosted_template` events.
- **Designed-template editor gaps**: no line-height or letter-spacing controls (size/bold/italic/underline/align/colour/font all exist, whole-object and per-character). No canvas size choice — locked to 1000×1250 (4:5), though `canvasWidth`/`canvasHeight` are already stored per event so the data model is ready. `public/design-assets/` is still empty — templates reuse the icon/decoration registries rather than shipping illustration, which is the main reason cards can still read as plain.
- **Guests never see the event details on a `designed_template` card**: title/host/date/location/description are shown above the card for every *other* kind, but a designed card renders only the canvas. Deliberate ("metadata only, separate from canvas"), but it means a sender who fills in the Details tab sees that content nowhere, and `/sender/landing` promises "add the essentials — time, place, host." Open decision, still awaiting the user's call — see `NEXT_STEPS.md` §2C for the three options laid out.
- **The sender dashboard Overview and the logged-in admin gateway are both near-empty screens** — no counts, no recent activity. Likewise the invitation gallery shows a generic placeholder for every invitation except `custom_card` (which has a real uploaded image), despite designed cards having everything needed to render a real thumbnail.
- Every page's `<title>` is just "RSVP" — no per-page titles, including the guest page, which should carry the event's own title.
- RSVP `questions` still can't be edited after creation (`external_url` now can).
- No QR code generation on the guest page yet, despite the package being installed and never imported anywhere.
- No tests. The 2026-07-28 verification scripts were deliberately deleted after use rather than committed — they used `require()` and would have broken the clean-eslint invariant.
- No production deployment/hosting decision made.
- `SESSION_SECRET` still falls back to a committed dev value (a production build now throws rather than starting insecure). Admin credentials default to the committed pair unless `ADMIN_USERNAME`/`ADMIN_PASSWORD` are set.
- **Scratch test data in the dev DB**: as of 2026-07-28 the database is small — the user's own account plus a `statscheck1` / "Stats check party" pair (one hosted_template event with one attending RSVP) left behind by the statistics verification run. Not cleaned up; deleting rows is a destructive action that needs the user's say-so.
- **`hosted_template` has no creation entry point (2026-07-29)**: `/create/link` and `/create/template` — its only creation UI — were deleted as genuinely dead nav (confirmed with the user: `external_link` was never actually wanted and `hosted_template`'s route just happened to share the same fate since nothing pointed at either). `hosted_template` itself stays a fully real, wanted `EventKind` per the user's explicit confirmation ("hosted template and that is genuinely useful in real world") — the type, its DB constraint, `EventEditor`, and `GuestEventView` rendering are all untouched. It just currently can't be created from the UI at all; a new entry point (likely wired into `NewInvitationModal` alongside "Design in our editor"/"Bring your own card") is the obvious next step whenever the user wants it, not a decision made against it.
