# SYSTEM_MEMORY.md

Current technical truth for the RSVP app. Narrative history and working-style notes live in `CLAUDE.md`.

## Stack

- Next.js 16 (App Router), React 19, TypeScript, Tailwind CSS v4 — scaffolded via `create-next-app` on 2026-07-23.
- PostgreSQL via `pg` (no ORM), connection via `DATABASE_URL` env var.
- `nanoid` for short public slugs, `qrcode` installed but not yet wired into any page, `lucide-react` for all icons (never emoji — see UI and Design Rules), `ws` for the WebSocket server/client, `bcryptjs` for hashing user passwords (pure-JS, chosen over native `bcrypt` to avoid Windows build friction), `heic2any` (client-only, dynamic `import()`) to transcode HEIC/HEIF photos to JPEG in-browser before upload, `recharts` for the Statistics pie chart, `fabric` (v7, added 2026-07-28) as the canvas engine behind the designed-template invitation editor — see "Designed-template invitations" below. `react-rnd` (used by the original designed-template slot editor) was removed when that editor was rebuilt on Fabric.js.
- Dev server: `npm run dev` runs `node server.js`, pinned to **port 3001**, not the Next.js default 3000 — the user's other project (restaurant order tracker) already runs on 3000, and both projects may run side by side. `npm run start` also runs `server.js`. All scripts (`scripts/*.sh`, `scripts/*.ps1`) and docs reference 3001.
- **Custom `server.js`** (CJS, project root) wraps Next and hosts a raw `/ws` WebSocket endpoint — required because plain `next dev`/`next start` can't host a raw WS upgrade. Same-origin check on the WS upgrade (Origin header must match Host); no LAN/non-browser exception yet (unlike the reference project, RSVP has no non-browser client). Broadcasts a `{type: "heartbeat", status: "healthy", at: <ms>}` message every 10s to all connected clients (`globalThis.__rsvpWsClients`), plus one immediate heartbeat on connect. Also exposes its own `broadcast()` function on `globalThis.__rsvpBroadcast` (added 2026-07-24) so API route handlers — which run in the same Node process but through Next's request handler, not `server.js`'s own code — can push a live WS message without holding a WebSocket client themselves; see "Auth" and "WebSockets" sections below. `eslint.config.mjs` has a scoped override allowing `require()` in `server.js` only (it's a plain CJS entrypoint, not bundled by Next).
  - **Gotcha**: `server.js` only runs its top-level code once at process boot — it is not hot-reloaded by Next's dev-mode HMR. Editing `server.js` (e.g. adding the `__rsvpBroadcast` assignment) requires a full dev-server restart before API routes can see the new `globalThis` value; a plain file save is not enough. Confirmed via a `hasBroadcastFn: false` → restart → `hasBroadcastFn: true` check on 2026-07-24.
  - **LAN-reachable (2026-07-27)**: `server.js` binds to `0.0.0.0` (via `HOST` env var, default `"0.0.0.0"`) instead of localhost-only, so the app is reachable from other devices on the same network at `http://<this-machine-LAN-IP>:3001` — needed to test under real external-network conditions, not just from the machine running the server. `server.js` also stamps the real client socket address onto the `x-forwarded-for` header on every incoming request (always overwritten, never trusts an inbound value) before handing off to Next, since App Router route handlers have no other way to read the raw socket — this is what `src/lib/rate-limit.ts` and `src/lib/network.ts` key off. **Admin surfaces are deliberately excluded from this LAN exposure** — see "Localhost-only admin gate" below.

## Environment

- Local Postgres runs via Docker: `docker-compose.yml` defines a single `postgres:16` service, container name `rsvp-postgres-1`, port `5432`, db `rsvp_dev`, user/pass `postgres`/`postgres`, data in the named volume `rsvp-postgres-data`. Start with `docker compose up -d`, matching the other project's Docker-based local Postgres.
- Copy `.env.local.example` to `.env.local` (`DATABASE_URL=postgres://postgres:postgres@localhost:5432/rsvp_dev` — already matches the compose defaults). `.env*` is gitignored.
- `npm run dev` needs the container up first; `initDb()` migrates on first DB access per process, same as the other project.

### One-command start/stop

- `npm run start:all` (or `startup.cmd`, or `scripts/startup.ps1`/`.sh`): checks Node/npm/Docker, auto-launches Docker Desktop if needed (up to 90s wait, also brings up WSL), creates `.env.local`/installs deps if missing, starts Postgres, waits for it to accept connections, runs `npm run dev`.
- `npm run stop:all` (or `shutdown.cmd`, or `scripts/shutdown.ps1`/`.sh`): stops port 3001, stops the Postgres container (data preserved), **then fully quits Docker Desktop and runs `wsl --shutdown`** — machine-wide, not just this project, by explicit user request. Shuts down Docker Desktop gracefully via `docker desktop stop --timeout 30` (never `--force`), not a hard process kill — a hard kill was tried first and left `vmmemWSL` running since Docker's own WSL-backend teardown never got to run; force-kill is kept only as a fallback if the `docker` CLI is unavailable.
- `npm run db:up` / `db:down` alias `docker compose up -d` / the same full shutdown as `stop:all` (`db:down` also quits Docker Desktop + WSL, not just the container).
- Shared progress-bar/output-formatting helpers live in `scripts/_common.sh`/`.ps1`, sourced by both scripts rather than duplicated. Full cold-start-to-shutdown cycle live-verified on both the bash and PowerShell paths.

### Data model

`src/lib/db.ts` owns the Postgres pool (memoized on `globalThis` in dev to survive HMR) and `initDb()`, an idempotent migration runner memoized per-process — same shape as the reference project's `initDb()`. Called at the top of every route/page that touches the DB.

**`events`**
- `id UUID PK`, `slug TEXT UNIQUE` (nanoid, 8 chars, non-ambiguous alphabet — see `src/lib/slug.ts`)
- `kind TEXT CHECK IN ('external_link', 'hosted_template', 'custom_card', 'designed_template')`
- `title TEXT NOT NULL`, `host_name`, `description`, `event_date TIMESTAMPTZ`, `location`
- `external_url` — set only when `kind = 'external_link'`
- `questions JSONB` — array of `RsvpQuestion` (`{ id, label, type: 'text'|'boolean', required }`), set only when `kind = 'hosted_template'`
- `card_image_url TEXT` — a data URL (`data:<mime>;base64,...`), set only when `kind = 'custom_card'`; see "Image uploads" below
- `created_by UUID FK -> users(id) ON DELETE SET NULL` — the sender who owns this invitation
- `guest_categories JSONB DEFAULT '["Adults", "Kids"]'` — sender-defined category labels for the "how many of each" guest-count breakdown; see "Guest categories" below
- `published BOOLEAN DEFAULT false` — gates `/receiver/[slug]` and RSVP submission; only ever flips `false → true` via `PUT /api/events/[slug]` (see Routes table)
- `created_at TIMESTAMPTZ DEFAULT now()`

**`rsvps`**
- `id UUID PK`, `event_id UUID FK -> events(id) ON DELETE CASCADE`
- `guest_name TEXT NOT NULL`, `attending BOOLEAN NOT NULL`, `guest_count INTEGER DEFAULT 1` — stored derived sum of `category_counts`, kept for backward compatibility with anything reading it
- `category_counts JSONB DEFAULT '{}'` — per-category breakdown keyed by the event's own `guest_categories` at submission time (e.g. `{"Adults": 2, "Kids": 1}`)
- `answers JSONB DEFAULT '{}'` — keyed by the event's `questions[].id`
- `created_at TIMESTAMPTZ DEFAULT now()`
- Index on `event_id`

**`users`**
- `id UUID PK`, `name TEXT NOT NULL`, `username TEXT UNIQUE NOT NULL`
- `password TEXT NOT NULL` — bcrypt-hashed
- `raw_password TEXT` — dev-only plaintext mirror, same intentional technical-debt pattern as the reference project's `restaurants` table
- `created_at TIMESTAMPTZ DEFAULT now()`
- Linked to `events` via `events.created_by` — a sender's dashboard (`GET /api/sender/events`) shows only the events they created.

Types mirrored in TypeScript at `src/lib/types.ts` (`EventRecord`, `RsvpRecord`, `EventKind`, `RsvpQuestion`, `UserRecord`).

**Migration idempotency gotcha**: `migrate()` re-runs its full body whenever `initPromise` resets (every dev-server restart, or a Turbopack Fast Refresh reload of `db.ts`). Every `ALTER`/constraint statement must tolerate re-running against a DB that already has the change applied. Concretely bit us once: a constraint drop-then-add split across two separate `pool.query()` calls left a race window where a second `migrate()` could see the constraint gone and fail re-adding it. Fix: combine drop+add into one multi-statement query so they run as a single round trip — do this for any future constraint change too.

**Image uploads** (`src/lib/image-upload.ts`): a real codec allowlist, not a loose `image/*` check — accepts PNG/JPEG/WebP/GIF/AVIF (`ACCEPTED_IMAGE_TYPES`), enforced both client-side (`isAcceptedImageType`, the upload form) and server-side (`isAcceptedImageDataUrl`, inspecting the data URL's own declared MIME prefix in `POST /api/events` and `PUT /api/events/[slug]`) since a direct API call bypasses the client picker entirely. SVG is deliberately excluded — it can embed `<script>`/event handlers and isn't sanitized before being rendered back on the public guest page, a real stored-XSS path. HEIC/HEIF (the default iPhone photo format, which no browser decodes natively) is auto-transcoded to JPEG client-side via `convertHeicToJpeg()` (dynamic `import("heic2any")`, client-only — never imported into a server route, since the library touches browser-only globals at module load). **`isAcceptedImageDataUrlSize()` (2026-07-27)** enforces the same 5MB cap the upload forms already applied client-side — previously the server had no size check at all, so a direct API call could store an arbitrarily large data URL; checked against both `POST /api/events` and `PUT /api/events/[slug]`.

**External RSVP link scheme validation (2026-07-27)**: `POST /api/events` rejects any `external_link` event whose `externalUrl` isn't `http:`/`https:` (parsed via `new URL()`) — previously only checked for non-empty, so a sender could store a `javascript:` URL that would execute in a guest's browser on click. `GuestEventView`'s `isSafeExternalUrl()` re-checks the same condition before rendering the "RSVP now" `<a href>`, as defense in depth against any pre-existing bad data.

**Guest categories** (`src/lib/guest-categories.ts`): `parseGuestCategories(raw)` turns a sender's free-typed "Adults, Kids, Moms, Dads, Pregnant Penguins" into a trimmed, empty-token-filtered array, falling back to `DEFAULT_GUEST_CATEGORIES` (`["Adults", "Kids"]`) if nothing usable was typed. Applies to any RSVP-taking event kind (`hosted_template`/`custom_card`); the editor skips the field entirely for `external_link` events, which never show the hosted RSVP form. The guest-facing `RsvpForm` renders one number input per category plus a live-computed, non-editable total ("Adults + Kids = N"), generalized to however many categories the event defines.
- **Per-category count cap + input fixes (2026-07-27)**: each category's count is capped at `MAX_CATEGORY_COUNT = 999`, enforced both client-side (`RsvpForm.tsx`'s `CategoryCounts`, via `Math.min` in its `onChange`) and server-side (`POST /api/events/[slug]/rsvps`, same constant) — previously uncapped, so a client could type or a direct API call could send an arbitrary value like `999999999` and it would be stored as-is (aside from being floored to a non-negative integer). Also fixed two input UX bugs in the same component: the field previously always rendered `value={counts[category] ?? 0}`, a plain number, which caused a visible "01" while typing a fresh digit into a zeroed field (typing "1" briefly showed "01" as React reflowed the controlled value) — fixed by rendering the raw typed digit string directly (empty string shown as a `0` placeholder, not a real `0` value) instead of round-tripping through `Number()` on every keystroke. The Total display box was also a fixed `w-20`, which visibly overflowed for large totals — changed to `min-w-20 w-fit` so it grows with its content instead of clipping.

**Designed-template invitations**: a fourth `EventKind`, `designed_template` — the "Design in our editor" flow. Originally built 2026-07-27 as a template-constrained `react-rnd` slot system (3 fixed layouts, drag/resize named slots within guardrails); **rebuilt 2026-07-28 on a real Fabric.js canvas** after user feedback that the slot system couldn't add new text boxes, duplicate icons, or drop in arbitrary images — see `custom rsvp card designer.md` for the fuller history of both versions. Current mechanism:
- `events.design_config JSONB` (nullable, only set for this kind) stores `{paletteId?, fontPairId, colors, canvasJSON, canvasWidth, canvasHeight}` — `src/lib/design-types.ts`'s `DesignConfig` type. `canvasJSON` is Fabric's own `canvas.toObject(propertiesToInclude)` scene graph (objects, positions, colors, text content, embedded images as data URLs) — no custom scene-graph parsing is written or maintained; `canvasWidth`/`canvasHeight` fix the logical coordinate space so the same JSON renders identically at any container size. The old `templateId`/`slots`/`iconId` shape and `src/lib/design-templates.ts` were deleted outright (fresh start, no migration path for pre-rebuild designed_template events — confirmed acceptable with the user since the feature was still brand new).
- **Open colors, not fixed themes (2026-07-28)**: `colors: {background, text, textMuted, accent, onAccent}` is five independent free-form hex fields a sender sets directly (`src/components/design/ColorField.tsx` — a native color swatch + editable hex text input per role, `ColorFieldGroup` composes all five), per explicit user feedback that four fixed named themes felt uncreative/limiting and one of them ("Celebration," a yellow/brown pairing) read badly. `DESIGN_PALETTES` (`src/lib/design-palettes.ts`) still exists but only as **quick-pick presets** — clicking one fills all five color fields at once as a starting point; it's no longer the only option, and `paletteId` is now optional on `DesignConfig` (kept only so pre-2026-07-28 rows still resolve to something). Expanded from 4 to 8 presets in the same pass (Garden/Sunset/Elegant Evening/Classic Red/Ocean/Berry/Midnight/Citrus), each still real WCAG-checked.
- `sanitizeDesignConfig()` no longer rejects a request — it **only clamps/defaults** now (`src/lib/design-types.ts`), since only an event title is required to create or save a `designed_template` invitation, per explicit user instruction. A missing/invalid font id falls back to a caller-supplied default (the event's own current font on edit, `DESIGN_FONT_PAIRS[0]` on create); missing/invalid colors fall back to `DEFAULT_DESIGN_COLORS`; a malformed/oversized `canvasJSON` falls back to an empty canvas. `POST /api/events` and `PUT /api/events/[slug]` both dropped their old "palette, font pair, and card design are required" 400 response.
- **`fabric` (v7, no official React bindings)** is the canvas engine — chosen over Konva/PixiJS per the original research in `custom rsvp card designer.md` as "the more standard choice for a genuine design-tool feel." `src/components/design/FabricCanvas.tsx` owns the `<canvas>` ref + `fabric.Canvas` instance lifecycle directly (create on mount, dispose on unmount), exposing an imperative handle (`addText`, `addImage`, `addIcon`, `addDecoration`, `deleteSelected`, `bringSelectedToFront`/`sendSelectedToBack`, `recolorSelected`, `getJSON`, `hasSelection`, `getLayers`/`selectLayer`/`moveLayer`/`deleteLayer`) rather than a wrapper library. Renders in two modes off the same component: interactive editor (`readOnly=false`) and the guest-facing render (`readOnly=true`, every loaded object set `selectable: false, evented: false`) — same "editor and guest can never visually drift" principle the old `DesignedCardContent`/`SlotEditor` split held, now enforced by literally being the same component with the same `canvasJSON`.
- **Sizing**: a `ResizeObserver` measures the actual DOM container; Fabric's own `canvas.setZoom()` scales the fixed logical canvas to fit, rather than re-laying-out object positions — keeps `canvasJSON` coordinates meaningful at any render size (editor sidebar-cropped view vs. guest page vs. a future export).
- **Layer metadata + aspect-ratio lock**: every object gets a stamped `layerId`/`kind`/`label` (`kind` is `"text" | "image" | "icon" | "decoration" | "other"`) via `stampLayerMeta()` — Fabric doesn't include custom properties in `toObject()`/restore them via `loadFromJSON()` by default, so `FabricCanvas` always calls `canvas.toObject(["layerId","kind","label"])` (never plain `.toJSON()`) when saving, and Fabric's own `_fromObject` passes those same keys back in as constructor options on load, round-tripping correctly. Icons and decorations get `lockAspectRatio()` (`setControlsVisibility` hides the `ml`/`mr`/`mt`/`mb` edge handles, leaving only corner handles which always scale both axes together) — added 2026-07-28 after the user found resizing via a side handle could squash an icon; images are deliberately exempt (free non-uniform resize, e.g. cropping to a specific box, stays useful there). The lock is re-applied on `loadFromJSON` too, since control visibility isn't itself a persisted Fabric property.
- **Layers panel** (`src/components/design/LayersPanel.tsx`): a plain display list, not a live subscription — `FabricCanvas.getLayers()` is a pull-based snapshot (front-to-back order, matching how a layers list is normally read), and the parent page re-reads it on every `onChange`/`onSelectionChange` callback (add/delete/modify/select) and passes the fresh array down as a prop. Supports select (click a row to select that object on the canvas), reorder (bring-forward/send-backward buttons, backed by `canvas.moveObjectTo()`), and delete. Added 2026-07-28 after the user reported "layers, right now it's a mess" — confirmed working end-to-end (reordering visually changes which object draws on top, e.g. two overlapping icons swapping front/back).
- `src/lib/design-fonts.ts` — **expanded from 4 to 30 curated font pairs** (2026-07-28) across 7 moods (`DesignFontMood`: signature/editorial/script/playful/elegant/modern/seasonal), each still statically imported via `next/font/google` in `layout.tsx` exactly like the app's own two fonts (unchanged constraint: `next/font` resolves/subsets at build time, a sender still can't load an arbitrary Google Font at runtime). `layout.tsx` now statically imports ~50 individual font families across the 30 pairs. `DesignFontPair.scriptCaution?: boolean` flags pairs whose display font is too dense/decorative for long body text (advisory caption in the picker UI, not enforced).
- `src/components/design/FontPicker.tsx` — the font-pair picker's own self-contained, internally-scrolling panel (`max-height: min(28rem, 45dvh)`, so it adapts to actual screen size rather than a fixed px value) grouped by mood, each row a live preview whose own font size scales with the row's width via `cqw` container-query units (same pattern `DesignedCardContent` used to use for card text) rather than a fixed size. Added 2026-07-28 after the user asked for a font picker that's "scaleable and aware of its size and screen size" with in-panel scrolling.
- `src/lib/design-icons.ts` — expanded from 8 to 27 curated `lucide-react` icons, plus a new `DESIGN_DECORATIONS` registry (4 hand-authored decorative SVG motifs: flourish, confetti burst, sparkle cluster, dotted corner) rendered as `fabric.Path`/`fabric.Group` objects. ## Auth

Added 2026-07-24. Two independent, unrelated auth systems — ported from the reference project's own admin/kitchen split (admin credentials are recorded in `CLAUDE.md`'s "Critical — Read First" section):

- **Admin** — a single hardcoded username/password pair checked in `POST /api/admin/login` (plaintext string comparison, no DB row, no bcrypt — matches the reference project's own pre-public-launch tech debt, flagged as the first thing to move to env vars before any non-local deployment). The login form itself is inline on `/` (`AuthCard` in the gateway page's main content area when no admin session exists), not a separate `/admin/login` route — matches the reference project's own layout exactly, per explicit user instruction ("in the empty space on the right of the sidebar, it will have a login window like how restaurant has it").
- **Sender** — real, DB-backed, self-serve. `/sender/login` checks `GET /api/sender/has-account` first; if the `users` table is empty, it redirects straight to `/sender/signup` before ever rendering a login card (so a fresh install can't dead-end at a login form with nothing to log into). `/sender/signup` is a real self-serve registration form (bcrypt-hashed password, `raw_password` dev mirror, live `StrengthMeter`), auto-logs-in on success.

**Session mechanism** (`src/lib/session.ts`, ported from the reference project's own `lib/session.ts`): a stateless, signed HMAC token — `base64url(JSON payload) + "." + HMAC-SHA256(payload)` — not a JWT, not a DB `sessions` table. `verifySessionToken` uses `timingSafeEqual` on the signature and checks the payload's own `exp` claim. `SESSION_SECRET` env var with a dev-only hardcoded fallback (console warning if unset). Two separate cookies (`admin_session`, `sender_session`) so both roles can be logged in independently in the same browser without one login clobbering the other's cookie/remember-me duration — same rationale as the reference project's `admin_session`/`restaurant_session` split.

**Cookie options**: `httpOnly`, `sameSite: "lax"`, `secure` gated on `FORCE_SECURE_COOKIES === "true"` (explicit opt-in, not tied to `NODE_ENV`, since `NODE_ENV` reflects build mode not actual transport). **Remember Me** controls only the cookie's `maxAge` at set-time — 30 days if checked, 1 day if not (a real explicit value, not an omitted-`maxAge` session-only cookie, which the reference project found unreliable across ordinary browser navigation). The signed token's own internal `exp` is always 30 days regardless, an outer safety bound independent of cookie persistence.

**Enforcement layers** (`src/lib/auth.ts`): `requireAdmin()` / `requireSender()` are the real security boundary — every admin-gated API route calls one as its first line and returns its 401 response early if unauthorized. Pages additionally do a client-side `GET /api/session` check + redirect for UX (no flash of protected content), but that's not the actual gate — confirmed via a direct unauthenticated `curl` to `GET /api/dev/db` returning a real 401, not just a client-side bounce.

**Gated behind `requireAdmin()`**: the `/admin/db` page itself (client-side redirect to `/` if no admin session) plus its backing routes — `/api/dev/db` (GET/POST/DELETE), `/api/users/[id]` (PUT/DELETE), `/api/users/[id]/password` (PUT), `/api/events/[slug]` DELETE only (GET stays public).

**Gated behind `requireSender()` + ownership check** (event's `created_by` must equal the caller's `userId`, not just a valid sender session): `PUT /api/events/[slug]`, `GET /api/events/[slug]/rsvps/stats`. **Gated behind `requireSender()` alone** (no ownership check needed — creates a new row / lists the caller's own): `POST /api/events`, `GET /api/sender/events`.

**Localhost-only admin gate (2026-07-27)**: now that `server.js` binds to `0.0.0.0` for LAN testing, admin-only surfaces are additionally restricted to requests originating from the machine running the server — LAN reachability was meant for the sender/receiver-facing app, not the admin console (one hardcoded credential pair, full DB read/write/purge). Two layers, both keyed off `src/lib/network.ts`'s `isLocalhostIp()`/`clientIpFromHeaders()` (reading the same `x-forwarded-for` header `server.js` stamps with the real socket address — see the LAN section above):
- **`src/proxy.ts`** (renamed from `src/middleware.ts` same day — Next.js 16 deprecated the `middleware.ts` convention in favor of `proxy.ts` for the same request-interception mechanism; the rename is a straight file/export-name swap, no behavior change, re-verified after) — matches `/`, `/admin/*`, `/api/admin/*`, `/api/dev/*`, `/api/users/*` and returns a 404 (page routes) or `{error: "Not found"}` (API routes) for any non-localhost IP, before the request reaches a page or route handler at all.
- **`requireAdmin()` (`src/lib/auth.ts`)** — independently re-checks the same localhost condition (404 if not local) before checking the session cookie. This exists because `DELETE /api/events/[slug]` shares a path with the public `GET`/`PUT` handlers on that same route, so the proxy's path-prefix matching can't gate it — `requireAdmin()` is the only enforcement point for that one route, and every other admin route gets the check twice (redundant, not a gap). This split also matches Next's own stated reasoning for deprecating `middleware.ts` (a real CVE where auth logic living only in the edge-runtime proxy layer could be bypassed under load) — this app's proxy only ever does an IP check, never session/auth verification, which has always lived in route handlers/pages instead.

Live-verified from both localhost (admin routes reachable, correct 401 when unauthenticated) and the real LAN IP (admin routes 404, sender/receiver routes still 200); a spoofed `X-Forwarded-For` has no effect since `server.js` always overwrites it with the real socket address.

**Rate limiting (2026-07-27)**: `src/lib/rate-limit.ts` — in-memory, fixed-window, keyed by client IP (via the same `x-forwarded-for` mechanism) + a bucket name, stored on `globalThis` to survive HMR like the app's other module-level state. Applied only to the routes an unauthenticated outsider can actually hit (authenticated sender/admin routes are already gated by session, so weren't given IP limits — avoids throttling the sender/testers when they share one router's IP): `POST /api/admin/login` (10/5min), `POST /api/sender/login` (10/5min), `POST /api/sender/register` (5/hour), `POST /api/events/[slug]/rsvps` (20/10min). Returns 429 with a `Retry-After` header when exceeded. In-memory (not Redis-backed) is an intentional scope decision, not an oversight — this is a single-process app, and the goal is blunting naive scripted abuse, not surviving a multi-instance deployment.

## WebSockets

- `src/lib/useWebSocket.ts` — reusable client hook (connect to `/ws`, JSON parsing, reconnect with exponential backoff capped at 15s, returns `{status, messagesByType}` keyed by message `type`). Any live feature subscribes to its own `type` over this one connection rather than opening a second socket.
- `HealthPin` polls `GET /api/health` (not WS-driven) for DB round-trip latency/size/pool stats, live WS listener count (still sourced from `globalThis.__rsvpWsClients`, via HTTP now), and the client's own round-trip time. Tiered `healthy`/`ok`/`bad`/`terrible`, 10s idle / 1.5s active-popover poll cadence, debounced-250ms fetch-on-open, pauses when the tab is backgrounded. `/api/health` itself has no auth gate (matches the reference project's own kitchen-facing exposure pattern).
- **`db-changed` broadcast**: `server.js` exposes `broadcast()` on `globalThis.__rsvpBroadcast` (see Stack section). `src/lib/ws-broadcast.ts` wraps it as `broadcastDbChanged(kind: "users" | "events")`, called from every route that writes a `users`/`events` row, immediately after the write succeeds.
- **Subscribers**: `/admin/db` (refetches `GET /api/dev/db`); `GuestEventView` (refetches `GET /api/events/[slug]` — a guest with the page open sees a host's live edit); `StatsModal` (refetches stats while open, so a new RSVP updates the pie chart without a manual reopen).

## UI and Design Rules

- Theme is implemented per `theme.md` (full research/rationale/token table lives there). Fonts: Bricolage Grotesque (`--font-display`, headings only) + Plus Jakarta Sans (`--font-body`, everything else), loaded via `next/font/google` in `layout.tsx`. Colors: full light/dark CSS variable set in `globals.css` — `--color-bg-base`/`-bg-raised`, `--color-text-primary`/`-muted`, `--color-accent-coral`/`-coral-text`/`-on-coral`, `--color-accent-sage`/`-on-sage`, `--color-accent-lavender`/`-on-lavender`, `--color-border`, `--color-danger`, plus a structural layer added 2026-07-24: `--radius-sm`/`-md`/`-full`, `--color-surface-0`/`-1`/`-2`, `--color-border-strong`, `--color-success` (radius values ported directly from the reference project since they're theme-neutral; surface/border-strong/success derived from our own palette). Theme switches via a manual `data-theme` attribute on `<html>` (set by `ThemeToggle`, applied pre-hydration by an inline script in `layout.tsx` — same mechanism as the reference project) with `prefers-color-scheme` as the fallback when no manual choice has been made yet.
- **Color palette corrected 2026-07-24** — see `theme.md`'s "2026-07-24 correction" note for the full before/after table and WCAG math. Short version: the original coral (`#E4633F`/`#B8431F`) was mathematically orange, not coral-pink, and the original backgrounds (`#1E1B19`/`#2A2522` dark, `#FBF6EE` light) were RGB-close enough to the reference project's own warm-brown surfaces that the built UI read as a copy of it. Corrected to a genuine pink-red coral and real saturated hue backgrounds (bright pink-blush light `#FDF2F5`, deep plum/wine dark `#241827`). Sage and lavender were also defined as tokens from day one but never actually referenced by any component — every accent defaulted to coral, which was the real mechanism behind the "everything looks orange" complaint. Now sage drives "on" states (UI size toggle active pill, `AccessibilityMenu`'s toggle-open state and its switches) and lavender drives selection state (`AccessibilityMenu`'s CVD radio group) plus the gateway wordmark and Access DB nav icon; Sender nav icon stays coral, Receiver is sage. New `--color-on-sage`/`--color-on-lavender` tokens were needed because dark mode's lightened sage/lavender fail contrast against plain white text (sage vs. white is only 2.00:1) — they pair with a dark, same-hue-family text color instead, same pattern as the existing `--color-on-coral`.
- **Icons are always `lucide-react`, never emoji.** Emoji was tried first on the admin page and explicitly rejected by the user (2026-07-23) — emoji ignore theme color tokens and read as low-effort next to a real icon set.
- CSS custom properties (`--color-*`), never literal Tailwind color utility classes in components — same convention as the reference project.
- **Real accessibility system, ported from the reference project's actual source** (not just its docs) on 2026-07-24: `AccessibilityMenu` dropdown with three independent boolean toggles (High Contrast → `[data-contrast="high"]`, Reduce Motion → `[data-motion="reduced"]`, Enhanced Focus Outline → `[data-focus="enhanced"]`) plus a colorblind-palette radio group (`[data-cvd="deuteranopia"|"protanopia"|"tritanopia"]`, swaps the coral/sage/lavender accent hues). Persisted via localStorage + data-attributes, same pre-hydration-script pattern as theme. `src/lib/accessibility-prefs.ts` is the get/set contract.
- **High contrast / CVD palette specificity bug fixed 2026-07-24**: `[data-contrast="high"]` and `[data-cvd="..."]` (specificity 0,1,0) were silently losing the CSS cascade to `:root[data-theme="dark"]` (specificity 0,1,1) whenever dark mode was active — which it is by default (`prefers-color-scheme` fallback). Found via headless-Chrome computed-style inspection (`getComputedStyle(...).getPropertyValue('--color-...')` before/after toggling the attribute), not just visual screenshot comparison, since the visual delta was subtle enough to miss by eye. Fixed by anchoring both selectors to `:root` (`:root[data-contrast="high"]`, `:root[data-cvd="..."]`) to match the theme rule's specificity.
- **Real collapsible Settings pill** (`SettingsToggles.tsx`), not a static pill — collapses to a single Settings-icon square (fixed `2.5rem` width; leaving width unset let the pill's own border collapse toward zero-width, where left/right border edges visually merged into a stray line — fixed 2026-07-24), unravels leftward on click to a measured width (`ResizeObserver`-driven, via `useReservedTopRight`) revealing `HealthPin` → UI size (S/M/B) → `AccessibilityMenu` → `ThemeToggle`. Supporting hooks: `useDropdownReveal` (mount/unmount lifecycle for hover/click popovers so a closing animation can play), `useReservedTopRight` (publishes the pill's real measured size as CSS vars so in-flow content, e.g. `PageHeader`, can reserve clearance via the `.clear-top-right` class).
- **Globally mounted (2026-07-27)**: `GlobalSettingsToggles.tsx` wraps `SettingsToggles` and is mounted once in the root layout (`src/app/layout.tsx`), replacing three separate per-page mounts (`/`, `/sender`, `/admin/db`) that left the pill missing everywhere else — including the editor (`/e/[slug]`) and every guest-facing `/receiver/[slug]` page, which previously had no way to reach theme/accessibility/UI-size controls at all. `GlobalSettingsToggles` reads `usePathname()` to decide what `health` content to pass: `/admin/db` gets `<HealthPin showDbSize detailLevel="full" />`, `/` gets a plain `<HealthPin />` only once an admin session is confirmed (via `GET /api/session`), everywhere else gets a plain `<HealthPin />` (which defaults to `detailLevel="basic"`).
- **`HealthPin` detail levels (2026-07-27)**: new `detailLevel?: "basic" | "full"` prop, default `"basic"`. `"full"` (only ever passed on `/admin/db`) shows DB pool stats and live WS listener count in the popover on top of the always-shown connection/DB latency; `"basic"` (the default everywhere else, including the sender dashboard) omits both — those internals aren't meaningful outside the admin console, and previously showed on the sender dashboard by accident (it was passing a bare `<HealthPin />`, which used to mean full detail).
- **`PageHeader` gained a `noClearTopRight` opt-out prop 2026-07-24**, used by `/admin/db` only. The pill is a `fixed` overlay — it should draw on top of other UI when it expands, not have other UI live-shift to avoid it. `clear-top-right`'s reserved-space padding is driven by a CSS var that updates as the pill expands/collapses, which on `/admin/db` (a header with a busy action row: Seed/Purge/Back) was visibly shoving the action buttons left in real time. Fixed by having that page opt out of `clear-top-right` entirely and instead give its one genuinely crowded button (Purge Database) a small **static** `mr-14` margin — just enough clearance from the pill's *collapsed* resting position, that doesn't grow/shrink as the pill opens. The transient hover/tap health-detail popover still briefly overlaps the header when open — treated as acceptable, same category as any tooltip/dropdown overlapping content while open, not a persistent layout issue.
- Small reusable primitives ported/reskinned from the reference project: `Button`, `Card`, `PageHeader`, `ThemedTooltip` (hover tooltip driven by React state, not the native `title` attribute).
- Several `react-hooks/set-state-in-effect` ESLint findings are intentionally suppressed (with inline comments explaining why) in `ThemeToggle`, `UiSizeToggle`, `AccessibilityMenu`, `useDropdownReveal`, `HealthPin` — each is syncing to real DOM/localStorage state on mount (unavoidable without diverging from SSR) or an external system tick, matching the reference project's own documented precedent for the identical pattern. Not blanket-disabled — each site has its own comment.
- **Custom 404 page (2026-07-27)**: `src/app/not-found.tsx`, themed to match the rest of the app (wordmark, coral "404", the settings pill still renders on top of it since it's globally mounted) instead of the default Next.js error page. As a single global file (App Router convention), it catches both unmatched routes and every existing `notFound()` call in the app (an unknown `/e/[slug]`, an unpublished `/receiver/[slug]` viewed by a non-owner) — no per-route 404 files were needed given the app's small route surface.
- **Tailwind v4's Preflight resets `button { cursor: default }`** (an intentional upstream accessibility-motivated change from earlier Tailwind versions) — every native `<button>` in this app was showing the plain arrow cursor instead of the pointer/"clicky" cursor on hover until this was caught and fixed 2026-07-24. Fixed globally in `globals.css` with `button:not(:disabled), [role="button"] { cursor: pointer; }` rather than patching each component's className individually. If a future button still shows the wrong cursor, check whether it's disabled (correctly gets `cursor-not-allowed` instead, see `Button.tsx`) before assuming the global rule broke.
