## Critical — Read First

- **Never edit a source file through a terminal command.** Use the editing tools only. On 2026-07-28 a `(Get-Content f) -join '' | Set-Content -NoNewline f` collapsed all 65KB of `FabricCanvas.tsx` onto a single line and destroyed working code; the user had to intervene ("i restored whatever you broke, be careful moving forward"). Recovery came from VS Code local history (`%APPDATA%\Code\User\History\<hash>\entries.json` maps `resource` → file URI, `entries[]` → `{id, timestamp}`; pick the newest snapshot that still contains newlines). Two things learned in that recovery: restoring a file is `Copy-Item` of a backup (byte-faithful) and never a content transform; and **after an external write the editor buffer and disk can disagree** — `read_file`/`grep_search` served VS Code's in-memory buffer while `npx tsc` read disk, reporting different content and line numbers for the same file. Cross-check with `Get-Content` before trusting either; one edit through the edit tool flushes the buffer to disk and re-syncs them.
- **Admin credentials**: username `darkglory`, password `R$vp@dm!n` — defined in `src/app/api/admin/login/route.ts`, now overridable via `ADMIN_USERNAME`/`ADMIN_PASSWORD` env vars (see `SYSTEM_MEMORY.md`'s "Auth" section for the mechanism). Requested to be saved here explicitly 2026-07-24 ("credentials must be saved to claude md (not now, later when i tell you to do md update)").
- **Never close Docker Desktop or the app's Node/dev-server process as "cleanup" after testing.** Restarting them (stop + start again) is fine when actually needed, but leaving them open at the end of a turn is the default — only the user decides when Docker/Node actually get closed for the session. Stated explicitly 2026-07-24 after a testing session ended with both closed as tidy-up, which the user did not want: "why the hell did you close docker and node? keep those open. never close them." If a test genuinely requires stopping a server (e.g. to test the shutdown script itself, or to free a port for a different test), that's fine — just don't default to closing things down "to leave a clean state" once verification is done.
- **Never blanket-kill Chrome.** The user actively uses their own Chrome browser alongside this work. For any headless/scripted browser check (screenshots, visual verification):
  1. Launch a separate headless instance with a unique `--user-data-dir` and `--remote-debugging-port=9222`, pointed at `about:blank` (not the target URL directly):
     - PowerShell: `& "C:\Program Files\Google\Chrome\Application\chrome.exe" --headless=new --remote-debugging-port=9222 --user-data-dir="$env:TEMP\chrome-headless-test-$(Get-Random)" --no-first-run about:blank`
     - Git Bash: `"/c/Program Files/Google/Chrome/Application/chrome.exe" --headless=new --remote-debugging-port=9222 --user-data-dir="/c/Users/$USER/AppData/Local/Temp/chrome-headless-test-$RANDOM" --no-first-run about:blank`
  2. Open tabs via the CDP HTTP endpoint (`PUT http://localhost:9222/json/new?<url>`), then drive/inspect/screenshot over CDP — don't pass the target URL as a launch arg.
  3. When done, stop ONLY that specific PID (find it via `netstat`/`Get-Process` filtered on port 9222 or the scratch profile path — never `taskkill /IM chrome.exe` or any name-based kill) and delete its `--user-data-dir` scratch profile.
- **Never simulate a server failure against a destructive endpoint, and never `page.unroute()` while a request is still in flight.** On 2026-07-28 a rollback test intercepted a `DELETE /api/users/:id` with a *delayed* fake 503 to watch the optimistic row come back; `page.unroute()` ran before that delayed fulfil completed, which **released the held request to the real server** and genuinely deleted a real user row (name `asdff`, username `asdf`). Nothing about the app was wrong — the test tooling did it. Pick a read-only endpoint to simulate failures against (aborting a `GET` works fine and proves the same rollback path), and if an intercept is unavoidable, use `route.abort()` (immediate, nothing is held) rather than a delayed `fulfill`, and only unroute once the action has fully settled.
- **Testing writes to the dev DB**: when a feature genuinely can't be verified without data, create it in an **isolated Playwright browser context** (`browser.newContext()`), never in the shared VS Code browser — logging in there would clobber the user's own live admin/sender cookies. Leave whatever rows the test created; deleting them is a destructive DB write and needs the user's say-so like any other.

## What this project is

An RSVP website. A host creates an RSVP page one of two ways, gets a shareable link, and guests open that link to RSVP:

- **Bring your own link** — host supplies a title + their existing external RSVP URL (Google Form, Partiful, etc). Our page is a thin branded landing page that hands guests off to that link.
- **Build a template here** — host fills in event details and picks a few RSVP questions (attending y/n, guest count, free-text/yes-no questions). We host the actual form and store responses.

Current milestone (2026-07-23): get a working end-to-end proof of concept for both flows — not a polished/customizable product yet. The user explicitly wants to first prove "yeah this CAN work" before expanding scope.

The app has two audiences: **RSVP Sender** (a host creating/managing an RSVP) and **RSVP Receiver** (a guest RSVPing) — named directly after the reference project's own Kitchen Portal / Customer Tracker split. `/` is the admin gateway page. RSVP Sender now has a real auth system (`/sender/login`, `/sender/signup`) and a real dashboard behind it — invitation gallery, creation flows, statistics. **RSVP Receiver is not a gateway nav item** (removed 2026-07 — see the "Publish flow" entry below): there's no single receiver "home," only per-invitation `/receiver/[slug]` links a sender generates and shares after publishing.

The single most serious finding was a **SQL LIKE-wildcard weakness in login** (`username ILIKE $1` — submitting `%` matched every user row), which turned "guess a username and its password" into "guess any one account's password." Worth remembering as a class of bug: `ILIKE` with a raw user value is never a safe equality check. Everything found was verified against a running server (74 automated checks) rather than reasoned about, and the throwaway test scripts were deleted afterwards instead of committed, since they used `require()` and would have broken the project's clean-eslint invariant.

**Font bug — worth not re-deriving.** The user reported fonts not changing. The root cause was *not* the font pipeline: `requestRenderAll()` defers to `requestAnimationFrame`, which browsers throttle to a standstill in a background tab, so every property was set correctly and the canvas simply never repainted. Discrete user-triggered canvas changes now call synchronous `renderAll()`. Two dead ends worth remembering — patching `CanvasRenderingContext2D.prototype.clearRect` does *not* detect Fabric rendering, and `document.fonts.check()` returns true when only the *fallback* face is loaded.

**Twice in one session, a full-page screenshot suggested a layout bug that didn't exist** (a card looking cropped or overflowing) when the page was simply scrolled. Measuring `getBoundingClientRect()` disproved both. Worth checking scroll position before reporting a visual bug on the editor or receiver pages.

**A hidden browser tab is the other false-alarm generator, and it burned a real chunk of time on 2026-07-28.** The editor looked badly broken — canvas rendering at full 1000×1250 and hanging off the viewport — and it was purely because the tab wasn't visible. Browsers suspend `requestAnimationFrame` in a background tab (already known, it's what caused the font bug) but **also stop delivering `ResizeObserver` notifications entirely**, including the initial one — and the canvas sizes itself from `ResizeObserver`. Check `document.visibilityState` before investigating any canvas sizing problem. Playwright's `bringToFront()` does not un-hide a page VS Code is keeping hidden; use whichever shared page is marked "(active)".

**Snapping/alignment guides (2026-07-28)** were built on Fabric v7's own `AligningGuidelines` extension rather than hand-rolled, after the user asked for research into "how Canva did it." Canva doesn't publish their algorithm — the search turns up help-center tutorials — but the technique is standard and the extension already implements the hard part. The genuinely novel bit was making it snap to the *card* (centre, edges, safe-area margin), which the extension doesn't do: rather than fork it, phantom rectangles are fed through its documented `getObjectsByTarget` hook. The user also asked for "x and y instead of just x lines or just y lines"; measurement showed both axes already snap in the same drag (released 7 card-px off centre on both, landed exactly on centre), so nothing was changed there — worth re-measuring before "fixing" it again.

**Text boxes hugging their content (2026-07-28)** came from a user report that resizing a box shifted it sideways. The geometry was never wrong — measured, the left edge held at 99.99995 of 100. What moved was the *centred text* re-centring inside a box that had ~180px of dead space each side, because boxes were created at a flat 80% of card width regardless of content. Fixing the dead space fixed the perceived bug. Worth remembering as a pattern: the user describes the symptom accurately, but the cause was one level away from where it looked.

**Transparent PNGs were already supported** when the user asked whether they'd show a checkerboard — verified by pixel-sampling the editor and the published guest page (card background visible through the cut-out, zero black pixels anywhere). The upload pipeline re-encodes to WebP specifically because it preserves alpha; the JPEG fallback would flatten it to black, and never triggered. No change was made. Checking before building mattered here.

**LAN was never a networking problem.** The user reported LAN access broken; the assumption (and the first two diagnoses offered) was firewall and bind address. The actual cause was Next.js 16 blocking `/_next/*` as cross-origin, so the page HTML returned 200 and every JS chunk was refused — a blank page that looks exactly like unreachability. Fixed with `allowedDevOrigins`. A Windows Firewall rule is separately needed for *other* devices; note that testing from the host machine to its own LAN IP does not cross the inbound firewall, so a local "LAN works" check proves nothing about a phone.

## Decisions Not to Re-Litigate Casually

- Postgres is the datastore, matching the other project's familiar patterns (`pg` client, no ORM). Local dev expects a reachable `DATABASE_URL` (see `.env.local.example`).
- Template builder starts as a simple form (title/description/date/location + a flat list of text/yes-no questions), no drag-and-drop visual editor for `hosted_template`/`custom_card` events — that's still deferred for those two kinds. `designed_template` events do have a real freeform canvas editor (Fabric.js, rebuilt 2026-07-28 from an earlier fixed-preset slot system) — see `SYSTEM_MEMORY.md`'s "Designed-template invitations."
- Slugs are short random strings (`nanoid`, non-guessable alphabet excluding ambiguous characters), not sequential ids — event links are meant to be shared/public.
- `initDb()` runs idempotent `CREATE TABLE IF NOT EXISTS` migrations on first DB access per process, same memoized-promise pattern as the other project. If the schema changes, everyone hitting the app after a deploy/restart gets migrated automatically — no separate migration runner yet at this stage.
- **Dev server runs on port 3001, not Next's default 3000.** The user's other project (restaurant order tracker) already occupies 3000 and both may run side by side ("order tracker uses port 3000, so this should use 3001," 2026-07-23). Applies everywhere: `package.json` scripts, `startup`/`shutdown` scripts, README.
- **`/` is the admin gateway; `/admin` is a redirect to `/`, not the other way around.** User's explicit framing: "localhost:3001 should be the admin page. /admin should redirect to localhost:3001, and if it's like /admin/smthoverhere then that's fine." So `/admin/db`, `/admin/sender` etc. (future real subroutes) live as actual pages under `/admin/*`, but the bare `/admin` path itself is just a redirect, and `/` is canonical — confirmed explicitly over the alternative (`/admin` canonical, `/` redirects) via a direct question.
- **`npm run stop:all` / `db:down` fully quit Docker Desktop and run `wsl --shutdown`, not just stop the Postgres container.** User explicitly wants this as default behavior (confirmed via direct question, "yes, do it by default") despite affecting the whole machine, not just this project. Shutdown must go through Docker Desktop gracefully (`docker desktop stop`), never a force-kill — a force-kill was tried first and user caught via Task Manager that `vmmemWSL` was still running afterward. See `SYSTEM_MEMORY.md`'s "One-command start/stop" for the mechanism.
- **5MB is a compression target for images, not a rejection** (2026-07-28, explicit: "if the image is above an upload limit just compress the image / each image should have a limit of 5mb"). Oversized photos are downscaled and re-encoded until they fit rather than refused — same spirit as the earlier HEIC decision to convert rather than reject.
- **Templates are a starting point, never a constraint.** Everything a template produces is an ordinary canvas object the sender can move, edit or delete; this is stated in the UI itself. Consistent with the long-running rejection of locked/fixed-slot designs.
